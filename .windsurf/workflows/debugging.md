# 系统化调试 (Systematic Debugging)

禁止猜测性修复。遵循 4 阶段根因分析流程，确保真正解决问题而非掩盖症状。

## 硬性约束

在定位根因之前，禁止修改任何代码。先理解，后修复。

## Phase 1: 复现与隔离

1. 确认复现步骤

收集以下信息：
- 错误消息全文
- 复现步骤（精确到操作序列）
- 预期行为 vs 实际行为
- 环境（浏览器/Node 版本、.env 配置）

2. 最小化复现

// turbo
```
npx vitest run
npx tsc --noEmit
```

- 能否通过单元测试复现？
- 能否在隔离组件中复现？
- 能否通过日志定位到具体函数？

## Phase 2: 假设与追踪

3. 列出可能原因（至少 3 个）

按可能性排序：
- 假设 A: [最可能] — 验证方法
- 假设 B: [次可能] — 验证方法
- 假设 C: [低可能] — 验证方法

4. 逐一验证假设

- 添加 `console.log` 追踪关键变量状态
- 检查 Zustand Store 快照（DevTools）
- 检查网络请求（API 参数和响应）
- 检查 ReactFlow 节点/边数据一致性

## Phase 3: 修复与验证

5. 定位根因后，编写回归测试

先写测试，确认它能复现 bug（RED 状态）。

6. 实施最小修复

- 优先上游修复，避免下游 workaround
- 单行修复优于重构
- 不要顺手修其他问题（scope creep）

7. 验证修复

```bash
npx vitest run
npx tsc --noEmit
```

- 回归测试从 RED 变 GREEN
- 所有现有测试仍然通过
- 手动复现路径确认已修复

## Phase 4: 复盘与防御

8. 记录根因和修复

更新 `.tasks/TASK_TRACKER.md` 记录：
- Bug 描述
- 根因分析
- 修复方案
- 影响范围

9. 加固防御

- 考虑是否需要额外断言/校验
- 考虑类似场景是否存在同类问题
- 考虑是否需要更新类型定义

## 常见陷阱

- 改了一个地方 "好像好了" 就停止调查 → 可能只是掩盖了症状
- 在不理解代码的情况下复制 StackOverflow 答案 → 引入新问题
- 同时修复多个 bug → 无法确认哪个修复生效
- 删除报错代码而非修复它 → 功能退化
