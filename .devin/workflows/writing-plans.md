# 编写实现计划 (Writing Plans)

将已批准的设计文档拆解为精确到文件级别的工程任务列表，每个任务 2-5 分钟可完成。

## 前置条件

设计文档已经过 `/brainstorming` workflow 生成并获得用户批准。

## 流程

1. 加载设计文档

// turbo
```
读取对应的 docs/designs/YYYY-MM-DD-<topic>.md
```

2. 拆解为工程任务

每个任务必须包含：
- 任务编号和简述
- 涉及的文件路径（精确到文件名）
- 要修改/创建的函数或组件
- 预期行为变化
- 验证命令（如何确认完成）

任务粒度：每个任务应该在 2-5 分钟内可完成。如果预估超过 5 分钟，拆分为子任务。

3. 排列依赖顺序

- 类型定义 → 数据层 → 逻辑层 → UI 层 → 测试
- 无循环依赖
- 每完成一个任务都不应该导致编译错误

4. 写入 TASK_TRACKER

```
编辑文件 .tasks/TASK_TRACKER.md
```

添加新的任务组，每个任务包含：
- 编号、描述、优先级、状态（pending）
- 关联的文件列表

5. 用户确认计划

展示完整任务列表给用户审阅：
- 任务是否遗漏
- 顺序是否合理
- 粒度是否合适

6. 开始执行

获得确认后，逐个任务执行：
- 标记当前任务为 `in_progress`
- 完成后标记为 `done` + 完成日期
- 每完成 3 个任务暂停，进行 checkpoint 检查

## 任务模板

```markdown
### T-XX: [简述]
- 文件: `path/to/file.ts`
- 修改: [函数/组件名] — [具体改动]
- 验证: `npx vitest run` 或 `npx tsc --noEmit`
- 状态: pending
```

## 关键原则

- YAGNI（You Aren't Gonna Need It）：只做设计中要求的，不提前扩展
- 每个任务完成后代码必须可编译
- 测试任务不能推迟到最后，应穿插在实现任务之间
- 遇到设计遗漏时，暂停并回到 `/brainstorming` 补充
